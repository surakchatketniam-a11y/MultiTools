# บทวิเคราะห์ผลิตภัณฑ์และแผนปรับปรุง UX — Multitools Calculator

วันที่วิเคราะห์: 14 ตุลาคม 2569 (2026-10-14)

สถานะ: ข้อเสนอสำหรับนำไปปรับปรุงภายหลัง ยังไม่ได้ดำเนินการตามรายการนี้ทั้งหมด

## ขอบเขตและข้อจำกัด

วิเคราะห์จากโค้ดปัจจุบันใน `index.html`, `sw.js`, `manifest.json` ภาพหน้าจอที่ผู้ใช้ส่ง และปัญหาการกรอกข้อมูลที่พบในเซสชันนี้ โดยใช้มุมมอง Lead Product Manager และ Senior UX Specialist

ข้อค้นพบระดับโค้ดแยกจากสมมติฐานด้านผลิตภัณฑ์ การวิเคราะห์นี้ยังไม่ใช่ผลทดสอบกับผู้ใช้จริงหรือการทดสอบทุกขั้นตอนในเบราว์เซอร์ จึงยังสรุปว่าเกิด Product Market Fit แล้วไม่ได้ ก่อนลงมือแก้แต่ละรายการควรตรวจสถานะโค้ดล่าสุดอีกครั้ง

## ทิศทางผลิตภัณฑ์

โปรเจกต์มีศักยภาพเป็น **เครื่องมือช่วยตัดสินใจเรื่องเงิน ต้นทุน และเวลา สำหรับผู้ใช้ไทย** จุดแข็งคือรวมเครื่องมือที่ใช้ในชีวิตจริง เช่น ราคาต่อหน่วย VAT ต้นทุนต่อพื้นที่ และวันทำการไว้ด้วยกัน

สิ่งที่ควรลงทุนก่อนเพิ่มฟังก์ชันคือ **ความถูกต้องของผลลัพธ์และความสม่ำเสมอของการกรอกข้อมูล** เพราะบั๊กในขั้นตอนกรอกทำให้ผู้ใช้ไม่มั่นใจในคำตอบทั้งหมด

ระดับความสำคัญในเอกสารนี้:

- **P0:** ผลลัพธ์ผิดหรือความเสี่ยงที่ทำให้ใช้ฟังก์ชันหลักไม่ได้
- **P1:** อุปสรรคในงานหลัก ความน่าเชื่อถือ และการนำผลไปใช้
- **P2:** การต่อยอดคุณค่าและประสบการณ์ระยะถัดไป

| จุดติดขัด | ผลต่อผู้ใช้ | แนวทางแก้ที่ทำได้จริง | ลำดับ |

| การกรอกมีทั้งช่องจริงและกล่องที่ต้องใช้แป้นร่วม | Enter, Tab, Space และการแก้ตัวเลขให้ประสบการณ์ต่างกัน | กำหนดกติกากลาง: พิมพ์และวางได้ทุกช่อง, Tab ไปช่องถัดไป, Enter จบการกรอก, คำนวณไม่ดึงโฟกัส | P1 |

| ผลลัพธ์บางหน้าไม่มีรายละเอียดสมมติฐาน | ตรวจคำตอบหรืออธิบายต่อไม่ได้ | เพิ่มวิธีคิดแบบพับได้ เช่น `864 ÷ 50 = 17.28 บาท/ชิ้น` และระบุหน่วยให้ครบ | P1 |

### การเข้าถึง

- เปิดให้ซูมข้อความได้ แทนการล็อก `user-scalable=no`
- เพิ่มพื้นที่กดของปุ่มปักหมุด
- ทำสถานะเลือกแท็บให้โปรแกรมอ่านหน้าจอเข้าใจได้
- ตรวจข้อความขยาย 200% โดยเนื้อหาและฟังก์ชันยังใช้งานได้ ตาม [WCAG: Resize Text](https://www.w3.org/WAI/WCAG21/Understanding/resize-text)

## 2. Feature Gap Analysis

รายการโปรด การเก็บสถานะ และตัวอย่างข้อมูลมีอยู่แล้ว สิ่งที่ควรเติมคือความสามารถในการนำคำตอบไปใช้งานต่อ

| ฟังก์ชันที่ควรเติม | รูปแบบที่แนะนำ | ลำดับ |
|---|---|---|
| คัดลอกและแชร์ผลลัพธ์ | คัดลอกข้อมูลตั้งต้น สูตร หน่วย และผล ไม่ใช่ตัวเลขอย่างเดียว | P1 |
| บันทึกชุดคำนวณและประวัติ | ตั้งชื่อ เช่น ราคาข้าวสารร้าน A/B แล้วเปิดกลับมาแก้หรือทำสำเนา | P1 |
| ตรวจข้อมูลผิดแบบรายช่อง | แจ้งจำนวนต้องมากกว่า 0 ใต้ช่อง พร้อมคงค่าที่ผู้ใช้พิมพ์ไว้ | P1 |
| เปรียบเทียบราคาที่หน่วยต่างกัน | เลือกกรัม/กิโลกรัม/มิลลิลิตร/ลิตร แปลงเป็นฐานเดียวก่อนจัดอันดับ เพิ่มชื่อสินค้าและจำนวนแถว | P1 |
| แสดงสถานะข้อมูลภายนอก | แยกเรทอ้างอิงล่าสุด ข้อมูลที่บันทึกไว้ และเรทกำหนดเอง พร้อมวันที่ของเรท | P1 |
| ปฏิทินงานที่ตั้งค่าได้ | เลือกวันทำงาน วันหยุดรายปี วันหยุดองค์กร และกติกานับวันเริ่มต้น | P2 |

### ประสบการณ์ออฟไลน์

- [ ] เชื่อม service worker จากไฟล์จริง

- [ ] ทดสอบเปิดแอปหลังตัดอินเทอร์เน็ต
- [ ] ทดสอบอัปเดตแอปเพื่อไม่ให้ผู้ใช้ติดอยู่กับไฟล์เก่าจาก cache

## 3. Edge Cases และข้อผิดพลาดที่ควรจัดการก่อน

| สถานการณ์ | สิ่งที่พบหรือความเสี่ยง | วิธีแก้ | ลำดับ |
|---|---|---|---|
| คำนวณวันที่ในเขตเวลาไทย | ใช้ `toISOString().slice(0,10)` กับวันที่ท้องถิ่น ทำให้วันลดลงได้หนึ่งวัน ตรวจแล้วว่าเที่ยงคืน 14 ต.ค. ในไทยแปลงเป็นวันที่ 13 ต.ค. ด้วยวิธีนี้ | จัดการวัน/เดือน/ปีโดยไม่ผ่าน UTC สำหรับงานคำนวณวันที่ | P0 |
| กรอกปี พ.ศ. สองหลัก `14/10/69` | ตัวแปลงปัจจุบันให้ ค.ศ. 1526 เพราะเติม 2000 ก่อนลบ 543 | กำหนดนโยบายปีสองหลักตามโหมด หรือบังคับสี่หลักพร้อมตัวอย่าง | P0 |
| API สกุลเงินตอบสำเร็จ | โค้ดอ่าน `payload.rates` แต่ API v2 คืน array อาจไม่อัปเดตเรท แต่แสดงเวลาอัปเดตและแหล่งข้อมูลเหมือนสำเร็จ | ตรวจโครงสร้างและคู่เงินที่ได้รับก่อนเปลี่ยนสถานะสำเร็จ | P0 |
| เปลี่ยนอายุปัจจุบัน/อายุเกษียณ | มี `retirementYears` แต่ช่วงเวลาคำนวณเงินฝากยังอ้าง `years` เดิม | ให้ระยะสะสมเงินสัมพันธ์กับอายุที่กรอก และเปิดเผยสมมติฐานระยะใช้เงินหลังเกษียณ | P0 |
| วางตัวเลข `1,000` | หลายฟังก์ชันใช้ `parseFloat` โดยตรง ซึ่งอ่านค่านี้เป็น `1` | ทำตัวอ่านตัวเลขกลาง รองรับตัวคั่นหลักพันและเลขไทย ปฏิเสธข้อความที่แปลงไม่ครบ | P0 |
| เลือกวันทำการหรือกฎวันหยุดผิด | หน้าจอป้องกันการปิดวันทำงานทั้งหมดแล้ว แต่สถานะที่โหลดกลับมายังควรตรวจซ้ำ; วันหยุดเป็นรายการวันที่คงที่ | ตรวจสถานะก่อนวนคำนวณ จำกัดช่วงค้นหา และใช้ปฏิทินวันหยุดรายปีที่ระบุแหล่งข้อมูล | P1 |
| ส่วนลดเกิน 100%, จำนวนเป็น 0, ค่าว่าง | บางฟังก์ชันแปลงค่าว่างเป็น 0 หรือคำนวณต่อโดยไม่มีข้อผิดพลาดรายช่อง | แยกยังไม่กรอก ข้อมูลผิด และผลลัพธ์เป็นศูนย์ กำหนดช่วงค่าของแต่ละฟังก์ชัน | P1 |

รูปแบบ API สกุลเงินอ้างอิง [เอกสาร Frankfurter: หลายสกุลเงินในคำขอเดียว](https://frankfurter.dev/it/python/)

### ประเด็นความครบถ้วนของฟังก์ชัน

- โค้ดค้นหาเมือง ปักหมุดเมือง และเวลาเพื่อการนัดหมายอยู่หลัง `return` ใน `createKeypadFieldHTML` จึงไม่ทำงาน ควรย้ายไปส่วนแสดงเวลาโลกและตรวจการโต้ตอบจริง
- ตัวเลือกของหน้าเงินตราควรตรวจการผูกเหตุการณ์คลิกช่องกรอก เพราะ `attachFieldClickListeners` อยู่ภายในเงื่อนไขที่ตรวจว่าเป็นหน้าเงินกู้
- ข้อความ `18 in 1` ไม่ตรงกับแค็ตตาล็อกปัจจุบันที่มี 22 เครื่องมือ ควรสร้างข้อความจำนวนจากแค็ตตาล็อกเพื่อไม่ให้คลาดเคลื่อนในอนาคต
- ปุ่มล้างข้อมูลและโหลดตัวอย่างควรตรวจให้ครอบคลุมทุกเครื่องมือ และการโหลดตัวอย่างไม่ควรลบค่าตั้งค่าอื่นที่ผู้ใช้กำหนดไว้โดยไม่ตั้งใจ

## 4. Value Add Solutions และ Product Market Fit

### กลุ่มเป้าหมายที่ควรทดลองก่อน

ข้อเสนอเหล่านี้เป็นสมมติฐานที่ต้องพิสูจน์กับผู้ใช้จริง

1. **ผู้ซื้อของและผู้ค้ารายย่อย:** เชื่อมราคาต่อหน่วย → ส่วนลด → กำไร → VAT เป็นขั้นตอนเดียว ลดการกรอกตัวเลขซ้ำ เช่น ซื้อแพ็กใหญ่แล้วขายแยกชิ้นควรตั้งราคาเท่าไร
2. **ผู้ทำงานสำนักงานและธุรกิจขนาดเล็ก:** สร้างชุดคำนวณยอดรับสุทธิและวันครบกำหนด เชื่อม VAT/หัก ณ ที่จ่ายกับวันทำการ แล้วคัดลอกสรุปส่งต่อได้
3. **ผู้ทำเกษตร:** ทดลองต่อยอดต้นทุนต่อพื้นที่ด้วยการเปรียบเทียบวัตถุดิบหลายราคาและบันทึกต้นทุนต่อรอบ โดยเลือกกลุ่มหลักก่อนเพื่อให้การพัฒนามีเป้าหมาย

### คุณค่าสำหรับองค์กร

สร้างเทมเพลตที่ใช้ซ้ำได้ เช่น วันทำงานของบริษัท อัตราที่องค์กรใช้ และชุดคำนวณต้นทุน พร้อมชื่อผู้จัดทำ วันที่ และสมมติฐานในผลส่งออก

## ผลดำเนินงานรอบแรก — 15 ตุลาคม 2569 (2026-10-15)
